Nuxt can render the same app four different ways. The choice is per-route, not
per-app, and it's the single biggest lever on performance and hosting cost.

## The four modes

::note
Nuxt defaults to **universal rendering** (SSR) — HTML on the server, then
hydration on the client. You opt into the others per route.
::

| Mode | HTML built | Best for |
| ---- | ---------- | -------- |
| SSR | Per request, on a server | Dynamic, personalised pages |
| SSG (prerender) | Once, at build | Content that changes on deploy — docs, blogs |
| SPA | In the browser | Dashboards behind a login |
| Hybrid | Mix, via route rules | Real apps that are mostly one, partly another |

## Choosing per route

`routeRules` lets a single app mix strategies. This is how a marketing site and
an app dashboard live in one codebase:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  routeRules: {
    '/': { prerender: true },            // static homepage
    '/blog/**': { prerender: true },     // static content
    '/app/**': { ssr: false },           // client-only dashboard
    '/api/**': { cors: true }            // headers only
  }
})
```

::tip
This knowledge base is **fully prerendered** — every note becomes static HTML at
build time, so there's no server to run and search is instant.
::

## When SSG is the right call

::steps{level="3"}

### The content changes on deploy, not per request

Notes, docs and blog posts are written and committed, not generated live.

### You want the cheapest possible hosting

Static files serve from any CDN — no Node process, no cold starts.

### Search and navigation can be client-side

A prerendered index ships once and runs entirely in the browser.

::

## Related config

The generate command produces the static output:

```bash
npm run generate      # → .output/public, ready to deploy anywhere
```

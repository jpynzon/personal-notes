:kbd{value="ctrl"} + :kbd{value="z"} is fine when *you* typed the mistake. An agent
edits six files in one prompt — undo can't save you, and neither can your memory
of what those files looked like ten minutes ago.

Git can. You only need five commands.

## The problem

[OpenCode](/teaching/apps-dev/ai-prompts/opencode-cli) writes directly into your
project folder. That's the whole point — and it's also the risk. A single "make the
cart work" prompt can rewrite `script.js`, touch `index.html`, and quietly delete a
function you needed.

Without Git, your options are: notice immediately, or lose the work.

## The five commands

| Command | What it's for |
| ------- | ------------- |
| `git init` | Start tracking this folder. Once, at the beginning. |
| `git status` | Which files did the agent touch? |
| `git diff` | **What exactly did it change?** The review command. |
| `git add . && git commit -m "..."` | Save a good state you can return to. |
| `git restore .` | Throw away everything since the last commit. |

That's the whole toolkit for this course.

## Setup

::steps{level="3"}

### Tell Git who you are

Once per computer:

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
```

Use the same email as your GitHub account so your commits are credited to you.
This matters for pair projects — your grade depends on your commits appearing
under your name.

### Start tracking your project

From inside your project folder:

```bash
git init
```

### Create a .gitignore

Make a file called `.gitignore` in your project root:

```text [.gitignore]
node_modules/
.env
.opencode/
*.log
```

::warning
Your OpenCode API key is a password. If it ever lands in a file, that file goes
in `.gitignore` **before** your first commit. A key pushed to a public GitHub
repo is compromised within minutes — bots scan for them continuously.
::

### Make your first commit

```bash
git add .
git commit -m "initial project setup"
```

You now have a save point. Everything after this is recoverable.

::

## The working loop

This is the rhythm for every session with an agent:

```text
Plan mode  ──►  read the plan
                     │
                     ▼
Build mode ──►  agent edits files
                     │
                     ▼
              git diff  ──►  read what changed
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
      It's good              It's wrong
          │                     │
          ▼                     ▼
   git add .              git restore .
   git commit -m "..."    (back to last commit)
```

The `git diff` step is not optional. It is the only moment in the whole workflow
where you actually find out what the AI did, as opposed to what it *said* it did.
Those are different things more often than you'd like.

## Reading a diff

```bash
git diff
```

Lines starting with `-` were removed. Lines starting with `+` were added. Press
:kbd{value="q"} to exit.

Three questions while you read:

1. **Did it change files I didn't ask about?** Scope creep is the most common
   agent failure.
2. **Did it delete something?** Look hard at every `-` line.
3. **Can I explain each `+` line?** If not, ask the agent before you commit —
   not after.

::tip
`git diff` is long and ugly the first few times. Read it anyway. Two weeks in,
you'll be skimming it in fifteen seconds and catching things your classmates
ship straight to their repos.
::

## Undoing things

| Situation | Command |
| --------- | ------- |
| Agent made a mess, nothing committed yet | `git restore .` |
| Only one file is wrong | `git restore script.js` |
| The bad change is already committed | `git revert HEAD` |
| I just want to see my save points | `git log --oneline` |

::note
`git restore .` deletes uncommitted work permanently. That's the point — but it
means an uncommitted good change dies with the bad one. Commit often and this
never hurts.
::

## Commit messages

**You write the commit message. Not the agent.**

This is a real rule, not a style preference. Writing "renders product cards from
the products array" forces you to state what changed in your own words. If you
can't write the message, you don't understand the diff, and you shouldn't be
committing it.

Good:

```text
add renderProducts loop
fix total not updating after remove
show empty cart message
```

Bad:

```text
update
changes
fix bug
asdf
```

One commit per feature. Not one commit per session, and not one commit per
character.

## Habits worth keeping

::tip
- Commit **before** you prompt, so you always have a clean state to fall back to.
- `git diff` **before** you commit, always.
- If a build goes sideways, `git restore .` and write a better prompt. Do not
  try to argue the agent back to working code — it's slower than starting over.
::

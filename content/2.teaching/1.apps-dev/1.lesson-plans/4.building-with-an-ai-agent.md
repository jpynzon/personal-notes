Students have OpenCode installed and connected. They have never used it on
anything that matters. This session fixes that — and launches the project they
will work on for the rest of the semester.

The new skill this session is **reviewing work you didn't write**. Everything
before this taught students to write and read JavaScript. From here, the agent
writes most of the code, and the student's job shifts to directing it and
judging the result.

## Learning Objectives

After completing this lesson, students should be able to:

- Explain why an agent that edits files needs a version-control safety net.
- Initialize a Git repository and commit one feature at a time.
- Read a `git diff` and describe what changed in their own words.
- Use Plan mode to review an approach before any file is touched.
- Recognize the three most common agent failures: scope creep, silent deletion,
  and confident wrongness.
- Scope a semester-long project down to its smallest useful version.

## Materials

- OpenCode installed and connected to a model — see [OpenCode CLI](/teaching/apps-dev/ai-prompts/opencode-cli)
- Git installed, GitHub account created
- A throwaway folder for the live demo (**not** their capstone repo)

::warning
Verify OpenCode works for every student **before** this session, not during it.
Install problems will eat the entire two hours if you let them.
::

## Lesson Outline

::steps{level="2"}

### The Wreckage Demo

Open a small working project. Give the agent a deliberately vague prompt —
something like "make this better" or "add a cart" — in Build mode, with no Git.

Let it run. Then find the damage together: a renamed function, a deleted line,
a file nobody asked it to touch.

Ask the class: *how do we get back?*

There is no good answer. That's the point. Sit in the discomfort for a minute
before offering the fix.

### Git: Five Commands

Not version control theory. Five commands, framed entirely as damage control:

| Command | Purpose |
| ------- | ------- |
| `git init` | Start tracking |
| `git status` | What did it touch? |
| `git diff` | What exactly changed? |
| `git add . && git commit -m "..."` | Save a good state |
| `git restore .` | Throw the mess away |

Full walkthrough: [Git as Your Undo Button](/teaching/apps-dev/ai-prompts/git-as-your-undo-button).

Have every student `git init` their demo folder and make a first commit before
moving on. Then re-run the wreckage demo and recover with `git restore .`.

The recovery is the moment the lesson lands. Do it live.

### Reading a Diff

Spend real time here — this is the assessable skill of the second half of the
semester.

Run `git diff` on an agent change and read it together. Three questions:

1. Did it change files I didn't ask about?
2. Did it delete anything?
3. Can I explain every added line?

Introduce the rule that governs the rest of the course:

> **You write the commit message. Not the agent.**

If you can't summarize the diff in one line, you don't understand it yet.

### Plan Mode Before Build Mode

:kbd{value="shift"} :kbd{value="tab"} toggles the mode. Students already know
this mechanically; they have never used it with intent.

Give the same feature request in Plan mode. Read the plan as a class and find at
least one thing wrong with it — an unnecessary library, a misread requirement, a
step in the wrong order. There is almost always something.

Reject it. Refine the prompt. Get a better plan.

This connects directly to steps 4 and 5 of the [Prompt Flow](/teaching/apps-dev/ai-prompts/basic-prompting),
which students have read but not yet practiced with a tool that can act.

### Guided Build: One Feature, One Commit

Everyone builds the same small feature in their demo folder, following the loop:

```text
commit  →  plan  →  review plan  →  build  →  git diff  →  commit or restore
```

Cold-call two or three students to explain their diff before they commit. Do
this every session from now on — once students know the question is coming, the
review actually happens.

### Capstone Kickoff

Introduce the project that runs to the end of the semester:
[Semester Capstone](/teaching/apps-dev/activities/semester-capstone).

Cover the shape, not the details:

- **Pairs.** Both partners commit under their own name.
- **Vanilla HTML, CSS, JavaScript, and `localStorage`.** No frameworks, no
  backend, no login.
- **Milestones every week or two**, each one demoed in class.
- **Graded on what you can explain**, not on what your agent produced.

Emphasize the constraint that surprises them most: the stack ceiling is
deliberately low so that every line remains explainable. An impressive app they
can't defend scores worse than a modest one they wrote and understood.

### Pairing and Pitch Drafting

Pair students up before they leave. Unpaired students drift for a week and
never catch up.

Each pair drafts a one-paragraph pitch answering the three questions from
[Coding with AI](/teaching/apps-dev/lesson-plans/coding-with-ai):

- Who is this for?
- What problem does it solve?
- What is the smallest useful version?

Collect the drafts before dismissal — even rough ones. It commits them to a
direction and gives you a week to flag the projects that are too ambitious.

## Common Failure Modes to Name Out Loud

::warning
Students will hit all three of these. Naming them in advance means they
recognize them instead of panicking.

- **Scope creep** — you asked for one function, it refactored four files.
- **Silent deletion** — it removed working code to make its new code fit.
- **Confident wrongness** — it explains a bug to you in a calm, authoritative
  tone. The tone is not evidence.
::

## Assignment

Before the next session, each pair must:

1. Create a shared GitHub repository with both partners as collaborators.
2. Commit a `README.md` containing their pitch.
3. Start a reflection log — first entry covers the pitch decision and any
   scoping help they got from AI.

## Key Takeaways

::note
The tool changed. The responsibility didn't.

- An agent that edits files needs a safety net. That's Git.
- Plan mode is where you catch bad ideas — before they become bad code.
- `git diff` is the only place you learn what actually happened.
- You write the commit message, because writing it proves you understood it.

The course motto still holds:

> **You are the director. AI is the typist.**

A director who doesn't watch the footage isn't directing.
::

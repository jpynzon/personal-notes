You've built what I told you to build. Now you build something you chose, and you
keep building it until the semester ends.

Working in **pairs**, using **OpenCode** as your agent and **Git** as your safety
net, you'll ship a small application that solves a real problem for a real
person. Milestone demos every week or two. An individual defense at the end.

::note
The grade is not "did you produce an impressive app." The grade is **can you
explain the app you produced**. Those come apart quickly once an agent is
writing your code, which is exactly why this project exists.
::

## The Stack Ceiling

| Allowed | Not allowed |
| ------- | ----------- |
| HTML, CSS, vanilla JavaScript | Frameworks — React, Vue, Nuxt, Svelte |
| `localStorage` for persistence | Databases, servers, APIs, backends |
| Google Fonts, icon fonts via CDN | npm packages, build steps, bundlers |
| Multiple `.js` files | JavaScript libraries of any kind |

Your project must run by opening `index.html` in a browser. Nothing to install,
nothing to compile.

::warning
This ceiling is deliberate and it is not negotiable. Every line in your project
must be a line you can explain under questioning. The moment a framework is in
play, your agent starts producing code that is beyond what this course has
taught you to read — and your defense score collapses.

A modest app you understand beats an impressive one you can't defend. Every
time.
::

### Out of scope by design

- **No login or accounts.** `localStorage` cannot store passwords safely and
  you don't have a server. If your app needs "who is using this", use a name
  field or a dropdown.
- **No payments**, no email sending, no SMS.
- **No multi-device sync.** Data lives in one browser on one computer. Say so
  in your README.
- **No real-time / multiplayer.**

## Choosing a Project

Your app should do **one thing** for **one kind of person**. If your pitch needs
the word "and" more than twice, it's too big.

Some directions that fit the ceiling well:

| Idea | The one thing it does |
| ---- | --------------------- |
| Canteen order tracker | Staff log orders and see the day's total |
| Study flashcards | Students drill a deck and track which cards they miss |
| Barkada expense splitter | Log shared expenses, show who owes whom |
| Attendance logger | Mark a section present/absent, export the day |
| Gym workout log | Record sets and reps, see last week's numbers |
| Recipe box | Save recipes, scale ingredients by serving count |
| Class schedule builder | Build a weekly timetable, flag conflicts |
| Jeepney fare calculator | Pick a route, compute fare by distance and discount |

You may propose your own — most of the best projects are ones I didn't list.
Bring it to the pitch review.

::tip
The strongest capstones every semester are the boring ones with a real user.
"An app my mom would actually use for her sari-sari store" beats "a social
network for gamers" because you can ask your mom whether it works.
::

## Milestones

Each milestone is demoed in class on the date it's due. Bring a working browser
tab, not a slide.

::steps{level="3"}

### M1 — Pitch and Spec

**Due: Week 1**

- Shared GitHub repo, both partners added as collaborators.
- `README.md` containing your pitch: who it's for, what problem it solves, the
  smallest useful version.
- A feature list split into **must-have** and **later**. Three must-haves
  maximum.
- Reflection log started.

No code yet. Use [Prompt Flow](/teaching/apps-dev/ai-prompts/basic-prompting)
steps 1–3 to sharpen the pitch before you write it down.

### M2 — Data Model and Static Render

**Due: Week 3**

- Your data as an **array of objects**, hardcoded in JS for now.
- A reusable render function that turns that array into the page.
- Nothing interactive yet — but changing the array changes the page.

This is the Mini Product Store pattern applied to your own data. If you can't
describe your app as an array of objects, your scope is wrong — come see me.

### M3 — The Core Loop

**Due: Week 5**

The thing your app exists to do, working:

- Add an item through a form.
- Display the updated list.
- Remove or edit an item.

Data still disappears on refresh. That's expected at this stage.

### M4 — Persistence

**Due: Week 6**

- Data survives a refresh via `localStorage`.
- The app loads existing data on startup.
- A fresh browser with no saved data doesn't crash — it shows an empty state.

### M5 — Edge Cases and Polish

**Due: Week 7**

- Empty states everywhere a list can be empty.
- Form validation: no blank entries, no negative numbers, no nonsense dates.
- Confirmation before anything destructive.
- Readable on a phone-sized window.

### M6 — Freeze and Demo Prep

**Due: Week 8**

- **Feature freeze.** No new features after this date. Only bug fixes.
- README finished: what it does, how to run it, known limitations.
- Reflection log complete.
- Each partner prepares to explain a part of the code they did **not** write.

### Demo Day

**Week 9**

Five-minute demo per pair, then individual questioning. See
[The Defense](#the-defense) below.

::

::note
Milestones are gates, not suggestions. A missed milestone costs **5 points**
off your final grade, up to a maximum of 15. Showing up with something broken
counts as showing up. Not showing up doesn't.
::

## The One New Thing: localStorage

Everything else in this project uses JavaScript you already know. `localStorage`
is the one new API, and it's small.

It stores **strings only**, which means your array of objects needs converting
in both directions:

```javascript
const STORAGE_KEY = "capstone.items";

function saveItems(items) {
    localStorage.setItem(STORAGE_KEY, JSON.stringify(items));
}

function loadItems() {
    const saved = localStorage.getItem(STORAGE_KEY);

    if (!saved) {
        return [];
    }

    return JSON.parse(saved);
}
```

Then the pattern is always the same: change the array, save it, re-render.

```javascript
function addItem(item) {
    items.push(item);
    saveItems(items);
    renderItems();
}
```

::warning
`loadItems()` returning `[]` when nothing is saved is not a detail — it's the
difference between a working app and a blank white screen on first visit. Your
agent will often skip that check. This is exactly the kind of thing `git diff`
catches.
::

To inspect what's actually stored, open DevTools (:kbd{value="f12"}) →
**Application** → **Local Storage**.

## Process Rules

These are graded. They're also the entire point of the course.

::steps{level="3"}

### Plan before you build

Every feature starts in Plan mode (:kbd{value="shift"} :kbd{value="tab"}). Paste
the plan you accepted into your reflection log.

### Commit before you prompt

A clean commit before each agent run means `git restore .` is always available.

### Diff before you commit

Run `git diff`. Read it. If you can't explain a line, ask the agent — before
committing, not after.

### Write your own commit messages

If you can't summarize the change in one line, you don't understand it yet. See
[Git as Your Undo Button](/teaching/apps-dev/ai-prompts/git-as-your-undo-button).

### Both partners commit

Your commit history is evidence of your participation. A partner with no commits
under their own name has not participated, whatever the other partner says.

::

## The Reflection Log

Keep it in your repo as `REFLECTION.md`. One entry per work session — not one
entry per week written the night before it's due, which is obvious to read and
scores accordingly.

```markdown
## 2026-08-14 — Ana

**Building:** add-expense form

**Prompt used:**
> Add a form with fields for description and amount. On submit, push a new
> object to the expenses array and re-render. Don't touch renderExpenses.

**What the agent got wrong:**
It added the object but never called saveExpenses(), so refreshing wiped
everything. It also renamed my `expenses` variable to `expenseList` in two
places I didn't ask about.

**What I changed by hand:**
Added the saveExpenses() call after push. Reverted the rename with
git restore, then re-prompted with "do not rename existing variables".

**What I learned:**
Vague prompts invite the agent to tidy things I didn't ask it to tidy.
```

The "what the agent got wrong" section is the one I read most closely. An entry
where the agent was perfect every time tells me you weren't checking.

## The Defense

At Demo Day, each partner is questioned **individually** on code from your repo —
including code they didn't personally write. Expect questions like:

- Walk me through what happens when I click this button.
- Why is this a function instead of just repeated code?
- What does this line do if the array is empty?
- Show me where this data gets saved.
- You committed this change on Week 4. What problem was it solving?

::warning
Defense is scored individually. Two partners can and do receive different
grades from the same repository.
::

## Requirements Checklist

Before Demo Day, your project must demonstrate:

- [ ] At least one array of objects as the primary data structure
- [ ] At least four reusable functions
- [ ] At least one loop or `forEach()` generating page content
- [ ] At least one template literal
- [ ] At least two `addEventListener` calls
- [ ] `localStorage` save **and** load, with `JSON.stringify` / `JSON.parse`
- [ ] An empty state handled with an `if`
- [ ] Form validation that rejects bad input
- [ ] No hardcoded HTML for repeated content
- [ ] No per-item functions (`addRice()`, `addBread()`, …)
- [ ] Commits from both partners
- [ ] `REFLECTION.md` with entries spanning the whole project

## Grading Rubric

| Category | Points | Scored |
| -------- | -----: | ------ |
| Individual Defense — can you explain the code? | 25 | Individually |
| Working Application — does it do the thing? | 20 | Per pair |
| Data Modeling & Reusable Functions | 15 | Per pair |
| Git History & Process | 15 | Individually |
| Reflection Log | 15 | Individually |
| Persistence & Edge Cases | 10 | Per pair |
| **Total** | **100** | |
| Missed milestones | −5 each, max −15 | Per pair |

Note the weighting: **55 of 100 points are scored on you individually**, and the
single largest category is whether you can explain code an AI wrote. That is not
an accident.

## Stretch Goals

For pairs who hit M5 early:

1. **Export / import** — dump the data to a JSON file and read it back.
2. **Search or filter** the list without re-rendering everything.
3. **Sort** by more than one field.
4. **A settings panel** whose preferences also persist to `localStorage`.
5. **Keyboard shortcuts** for the most common action.

Stretch goals earn nothing if the required checklist isn't complete. Finish the
floor before you build the ceiling.

Transparent criteria for the end-of-unit web project. Share it with students
*before* they start — a rubric is a target, not a surprise.

## Criteria

| Criterion | Excellent (4) | Proficient (3) | Developing (2) | Beginning (1) |
| --------- | ------------- | -------------- | -------------- | ------------- |
| **Functionality** | All features work; handles edge cases | Core features work reliably | Core features mostly work | Frequent breakage |
| **Code quality** | Clear names, no duplication, well structured | Readable with minor issues | Works but hard to follow | Disorganised, copy-pasted |
| **UI/UX** | Polished, responsive, accessible | Clean and usable | Functional but rough | Confusing or broken layout |
| **Version control** | Frequent, meaningful commits | Regular commits | Few large commits | One commit / no history |
| **Documentation** | Clear README + comments where needed | Basic README | Sparse notes | None |

## Weighting

::note
Functionality and code quality each count for 30%; UI/UX 20%; version control and
documentation 10% each. Adjust to match what you emphasised in class.
::

## Using it well

::tip
Grade one criterion across all students before moving to the next. It's faster
and far more consistent than grading one whole project at a time.
::

::caution
Resist inflating "Functionality" because a student clearly worked hard. Effort is
real, but the rubric measures the artifact. Acknowledge effort separately.
::
